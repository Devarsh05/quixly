# 2026-07-31 — Phase 5: mandatory compliance webhooks

Implemented Shopify's three mandatory privacy webhooks — `customers/data_request`,
`customers/redact`, `shop/redact`. This is an App Store **submission gate**, not business logic:
the automated review posts test payloads to each endpoint (including one signed with a
deliberately invalid HMAC) and rejects the app if any of them misbehaves.

## The PII audit that shaped the design

Every model on both sides was read before anything was written, because the whole design turns on
the answer.

**Agent `public` schema** (11 models in `agent/app/models/`): `shops`, `products`, `ingest_runs`,
`query_panels`, `engine_runs`, `agent_runs`, `share_of_model`, `audits`, `fixes`, `verifications`.
All catalog or measurement data keyed by shop. The one that looked like a risk was
`query_panels` / `engine_runs` — but the queries are generated by `graph/interrogator`, so they are
synthetic and no real shopper is involved.

**App `shopify` schema**: Prisma owns `Session` only. It *does* carry `firstName`, `lastName`,
`email`, `userId` — but that is the **merchant's staff**, not the merchant's customers. In scope
for `shop/redact`, out of scope for `customers/redact`.

**Conclusion: no end-customer PII anywhere.** So two handlers acknowledge and one erases.

## Three corrections to the initial brief, all verified rather than assumed

1. **`[webhooks.privacy_compliance]` is the superseded CLI schema.** Current config uses
   `compliance_topics` inside `[[webhooks.subscriptions]]`. Confirmed twice: in the docs, and in
   the installed CLI's own Zod schema
   (`@shopify/cli/dist/chunk-R7QYSC6T.js`), which additionally rejects the two forms being used
   together. The same schema documents `uri` as accepting "a relative path starting with a slash",
   so the three new subscriptions use relative `uri`s like the three existing ones — no hardcoded
   host, and a future URL cutover moves all six at once.
2. **A missing HMAC header is 400, not 401.** `@shopify/shopify-api/lib/webhooks/validate.ts` has
   two distinct branches: `InvalidHmac` → 401, `MissingHeaders` → 400. Shopify's requirement (and
   the review probe) is about an *invalid* HMAC, which is the 401 path. The tests assert the real
   behaviour on both rather than forcing a 401.
3. **All three routes must use `authenticateWebhookSerialized`, not bare
   `authenticate.webhook()`.** `customers/*` arrive while the app is still installed, so a session
   exists and the library's `ensureValidOfflineSession` would refresh a near-expiry token *outside*
   the per-shop rotation lock — the second refresh path CLAUDE.md forbids. `shop/redact` normally
   has no session, which is fine: the wrapper already classifies that as `ReauthRequiredError` and
   passes through, and the HMAC uses the app secret, not the session.

## What was built

- `app/app/routes/webhooks.customers.data_request.tsx`, `.customers.redact.tsx` —
  verify → log shop+topic only → 200. **The payload is never logged**: it carries the customer's
  id, email and phone, and logging it would create the exact record the handler asserts we do not
  keep.
- `app/app/routes/webhooks.shop.redact.tsx` — verify → forward → `session.deleteMany` → 200.
  Forward first: a failure returns 500 so Shopify redelivers and the rows are still there to erase.
- `agent/app/services/purge.py` — `purge_shop_data`, plus the reinstall guard.
- `agent/app/jobs/purge_shop.py` — arq job; clears the Redis token cache + ingest lock, but only
  when rows actually went.
- `agent/app/api/webhooks.py` — `SHOP_REDACT` branch that enqueues and returns 204. Reuses the
  existing forward path so it inherits `_canonical_topic`, which is what stops the UPPER_SNAKE vs
  REST-form bug that silently no-op'd every forwarded webhook once before (`f0b97bc`).

## Notable findings

- **`app/uninstalled` deletes nothing.** It flips `shops.status` and drops the cached token; the
  catalog, audits, fixes and verification history all survive an uninstall by design. So
  `shop/redact` is not redundant with it — it is the first and only path that removes them.
- **The erasure is one `DELETE FROM shops`.** Every shop-scoped table cascades from it, and the
  `ON DELETE CASCADE` clauses are in the real DDL (checked in the migrations, not just in ORM
  metadata). The `SET NULL` FKs leave no orphans because each of those rows is reached by a CASCADE
  path of its own. The test asserts all nine tables individually anyway — the cascade is a claim
  until something checks it.
- **The reinstall guard is a judgment call, taken deliberately.** A shop found `active` is skipped
  with a warning. Purging a reinstalled store would destroy its uplift history, which cannot be
  recreated after the fact — there is no way to go back and take a baseline scan for a window that
  has passed.

## Verification

Run locally, all green:

- agent: `ruff check` clean; `pytest` **435 passed, 7 skipped**; Alembic drift check **empty**
  (no schema change, and the `shopify` fence still holds with `shopify.Session` present).
- app: `lint`, `typecheck`, `build` clean; `vitest` **111 passed** (10 files), of which **19** are
  the new `tests/compliance-webhooks.test.ts`.
- Build output confirms the three routes resolve to exactly the paths the TOML declares:
  `webhooks/customers/data_request`, `webhooks/customers/redact`, `webhooks/shop/redact`.

**Local test note (corrects an earlier assumption):** app DB-backed tests *do* run on this
workstation. `app/.env` has `DATABASE_URL` pointing at the local Docker Postgres but **without
`?schema=shopify`**, so Prisma looks in `public` and fails with "Error obtaining session table".
Overriding it in the shell works, and a shell value wins over `vitest.config.ts`'s `loadEnv`:

```powershell
$env:DATABASE_URL="postgresql://quixly:quixly@localhost:5432/quixly?schema=shopify"; npm test
```

## Not done here, deliberately

- **No scope change** and **no `SHOPIFY_API_SECRET` Old→New migration.** The TOML edit touches
  `[webhooks]` only, so it declares no permission and triggers no merchant re-consent. HMAC
  verifies against the Old secret, which is the one the released app version was created under.
